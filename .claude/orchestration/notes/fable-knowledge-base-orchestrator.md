**Current design (owner's decisions of 2026-09-18, evening):** the Fable knowledge base is discarded. One Opus implementer at max effort works alone as a fork of a sealed base; a plain daemon (`watchdog.py`) rotates it, restarts it after usage-limit stops and keeps the base warm; `start.sh` starts or rejoins and attaches, `stop.sh` stops everything. The base is downsized (target 540K loaded) and its purpose is to **bias the implementer's direction toward the owner's intent and the library's own ideas, not to serve lookups**: the owner's words, rules, plan, reasoning inventory, all theory names, and the *founding* theories of the library's ideas (presentations and local contracts, relational substrate, artifacts, generations/history, loci-selection-replacement-transactions, authority and currentness as a non-ambient relation, positive meaning, proofs, replay, admission, generalization machinery…), plus a measured frontier tier. The owner stressed the idea list is NOT exhaustive as named and must be curated deliberately from the library itself and from run data (`idea-candidates.md`, `qa.log`, what forks read and grepped); never build the base from a hand-picked list without the owner's curation. Theories and tools are held as **statements, not full files** (`digest.py`: definitions, locales, lemma statements and commentary verbatim; proofs replaced by a comment with their length and cited library facts; validated over all theories) — the owner's point: implementation details do not set direction. The owner wants ALL of the library's ideas in view, none discarded, because they steer values: so ideas are held at three resolutions — every theory by name, the founding theory of every vocabulary notion (244) as definitions + commentary + lemma names, and deliberately pinned idea theories as full statements; never cut inside a theory by usage (a citation-based cut dropped uniqueness and locality lemmas). Directions to an implementer go verbatim into `owner-ledger.md`.


**History.** On 2026-09-18 the owner first set this division of labour: a Fable session (`kb`) is the knowledge base and orchestrator — it answers the semantic questions of an Opus implementer working on native_control_plan.md, rotates the implementer, and itself never compacts and never runs code beyond the orchestration scripts. The same day the owner added: the rotation target is the whole window (not 850K), and live sessions should be forks of a loaded base session so that the knowledge is delivered from the prompt cache instead of being re-read and re-written cold — for the implementer and for kb alike — with the base's cache kept warm for reuse; both roles load the one list `base-load.txt`, sized to 700K tokens loaded with everything included (~300K of room per fork), whose measured tier `select_base_load.py` generates from what implementer sessions actually consulted. The implementation is `.claude/orchestration/` in the repository; its README is the runbook and lists what was verified and what was not.

Both bases were built and sealed on 2026-09-18 (kb base 691,439 tokens on Fable, implementer base 690,313 on Opus; a fork of each read it from cache with under 3.2K written); records are in `.claude/orchestration/state/*-base.json`, and a keep-warm daemon pings an unused base every fifty minutes for up to twelve hours.

First real run (2026-09-18 16:40): the account usage limit stopped kb and impl-1 after ten minutes and nothing restarts a background session at the reset — `watchdog.py` (run by the daemon every minute) now wakes them by `claude stop` + bare `claude --bg --resume <sid> "prompt"`, which keeps id, name, saved options, hooks and cache; a cross-session SendMessage also wakes an idle session. impl-1's first request read 0 tokens of its base for a reason not found (prompt and tools byte-identical; launcher and stop hook ruled out on small bases); rotate.sh/kb.sh now verify every fork's first request, and only a verified fork counts as keeping its base warm. A harness kills a session's background commands whenever the machine runs short of memory (three concurrent Isabelle runs reached 59 of 60 GiB), so nothing essential may live in a session's background task: kb holds no rotation waiter, the daemon's watchdog wakes it; supervision from a maintenance session uses CronCreate plus `.claude/orchestration/health.py`, not a background watcher. The owner authorized this maintenance session to restart and fix whatever is needed while away.

Measured cost of the 700K-base arrangement (2026-09-18, 17:40–19:00): 259M cache-read tokens in 1.33 h, about 22M input-equivalents per hour against about 11M for the owner's earlier single Opus session — the owner saw 52% of the plan window go in 1.2 h versus under 20% per hour before and stopped everything. Causes in order: every implementer request carried ~850K of context instead of ~500K (same request rate); two extra Fable sessions (kb ~770K per request, the maintenance session ~500K per request) added a fifth of the tokens on the most expensive model; rotations every ~17 minutes added handoff, briefing and kb turns. Any future design must be judged by context carried per request times requests per hour, across all sessions.

**Why:** compaction and tool output both destroy held knowledge; every Opus session so far spent roughly 200–280K tokens re-acquiring context after `/clear` + `/goal`, and ran to ~900–950K before the owner restarted it by hand.

**How to apply:** when acting as `kb`, follow `.claude/orchestration/kb-prompt.md`. Under the standing rule of DEVELOPMENT_WORKFLOW.md a kb answer is recall, a pointer, a candidate or criticism — never a decision and never evidence ([[owner-authority-order]], [[adequacy-current-basis]], [[inert-agents-native-decisions]]). A held file is a snapshot: the asker quotes current statements, and forks are told which held files are stale. Verified on Claude Code 2.1.273: an in-process fork and a session-level fork (`--bg --resume <base> --fork-session`, same model, effort and launch mode as the base) both read the parent's cache on their first request (a few hundred tokens written); background sessions do NOT inherit the launching shell's environment — pass settings via `--settings` `env`, never rely on exported variables (a test base loaded the real 554K-token list because of this); background sessions need `worktree.bgIsolation: none` here ([[isabelle-heaps-path-bound]]); auto permission mode needs Opus 4.6+/Sonnet 4.6+/Fable; this material tokenizes on Opus 5 at 3.05 characters per token for Markdown, 2.46 for Isabelle, 2.54 for Python (a Haiku-based 3.9 understated sizes by a third — never size a load from another model's tokenizer); a hand-picked load list was wrong (DECISIONS.md, ADMISSION.md, README.md never consulted; only 41 of 180 touched theories in the Native/Development/Isabelle families) — choose by measured use; the Read tool caps a call at 25K tokens, a file at 256KB and a line at 2,000 characters, so load lists name part sizes and folded copies. Never launch a second implementer while one is alive ([[large-batches-parallel-work]]); in `claude agents --json` the live field is `status` (busy/idle) — `state` can stay `working` long after a turn ended, so never report a session as still working from `state`; never `pkill -f` a pattern that occurs in the killing command itself ([[batched-callbacks]]).
